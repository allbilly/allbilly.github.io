rung m1 · +935 lines · 8 files · 36 tests

Our own fp32, bit-exact against our own model

PASS 2,118 vectors · whole value · no tolerance

The ISA's arithmetic is fp32 with unusual rules: round-to-nearest-even, flush denormals to zero, a single canonical NaN, and comparisons on the raw sign-magnitude bits rather than on numeric order. A "close enough" float library would be wrong here, so m1 writes two things: a Python model from the spec's prose, and RTL that must match it.

The single decision that made the rung tractable is that there is one rounding site. The adder is an exact integer add in an 8-guard-bit window; rounding happens once, in one function:

mini/rtl/fp32.svpack_fpthe only place in the branch where a float is rounded
// Pack: the one rounding site. `mag` is a magnitude whose leading one sits at bit `lead`;
// `exp` is the biased exponent of that leading one. Rounds ties-to-even, flushes denormal
// results, saturates to infinity.
function automatic f32_t pack_fp(input logic sign, input logic [63:0] mag,
                                 input integer lead, input logic signed [15:0] exp,
                                 input logic extra_sticky = 1'b0);
  logic [63:0] win;
  logic [23:0] frac;
  logic sticky, guard, rnd;

  if (mag == 0) pack_fp = {sign, 31'd0};
  else begin
    // normalize: shift the leading one to bit 26, folding the shifted-out bits into sticky
    if (lead > 26) begin
      sh = lead - 26;
      for (k = 0; k < 64; k = k + 1)
        if (k < sh && mag[k]) sticky = 1'b1;
      win = mag >> sh;
    end else begin
      win = mag << (26 - lead);
    end
    frac   = win[26:3];                       // 24 bits, MSB is the leading one
    guard  = win[2];
    rnd    = win[1];
    sticky = sticky | win[0] | extra_sticky;
    if (guard && (rnd || sticky || frac[0])) frac = frac + 24'd1;   // ties-to-even
    if (frac == 24'd0) begin            // significand carried into the next binade
      frac = 24'h800000;
      exp  = exp + 16'sd1;
    end
    if (exp <= 0) begin
      // Round on the subnormal grid. Landing exactly on 2^-126 is a NORMAL value and is KEPT;
      // anything smaller is denormal and flushes.
      if (exp <= -16'sd22) pack_fp = {sign, 31'd0};
      else begin
        shift = 1 - exp;
        frac2 = {1'b0, frac} >> shift;
        rem_bits = {1'b0, frac} & ((25'd1 << shift) - 25'd1);
        half = 25'd1 << (shift - 1);
        if ((rem_bits > half) || ((rem_bits == half) && frac2[0])) frac2 = frac2 + 25'd1;
        if (frac2 >= 25'h800000) pack_fp = {sign, 8'd1, 23'd0};   // rounded up to 2^-126: KEEP
        else                     pack_fp = {sign, 31'd0};          // still denormal: flush
      end
    end
    else if (exp >= 16'sd255) pack_fp = {sign, 8'hFF, 23'd0};    // overflow -> infinity
    else                      pack_fp = {sign, exp[7:0], frac[22:0]};
  end
endfunction

The corners the tests found

All real behaviour differences, none of them visible by reading:

  • an 8-bit exponent cast that wrapped 128 → −128;
  • inf + (−inf) must be the canonical +NaN, not a sign-preserving infinity;
  • a subnormal result the spec explicitly says must be kept — 0.5 × 0x00FFFFFF = 2−126;
  • a floor() off by one for negative fractions;
  • a sticky bit that never reached the rounding site — a genuine 1-ULP error where the model was right and the RTL was wrong.
Why the model comes first

That 1-ULP sticky bit is the argument for the whole rung. With no bit-exact oracle, a 1-ULP error looks exactly like success. The model pins the semantics; the RTL is only allowed to disagree with the model, never with the spec.

rung m3 · +1,101 lines · 4 files · 28 tests

Our own ISA encoder and reference machine

PASS 13 opcodes · 8 words per instruction

This is the rung that replaces 1,352 imported lines with 805 of ours. It has two halves: an encoder that says what the bits are, and a machine that says what they do. Keeping them separate is what makes the encoder testable on its own.

The instruction format is the whole of the ISA's addressing, so it is short enough to show in full:

mini/model/isa.pyw0one word carries the opcode, four registers and the flags
# w0 = opcode[7:0] | ra[11:8] | rb[15:12] | rc[19:16] | rd[23:20] | flags[31:24]

def word(op: int, ra=0, rb=0, rc=0, rd=0, flags=0) -> int:
    return (op            | (ra    << 8)  | (rb    << 12)
            | (rc  << 16) | (rd    << 20) | (flags << 24))

# only the thirteen the mini-core actually implements
OP_NOP  = 0x00;  OP_HALT = 0x01;  OP_LI   = 0x02;  OP_ADDI = 0x03
OP_LOOP = 0x04;  OP_BAR  = 0x05;  OP_RLD  = 0x06
OP_LD   = 0x10;  OP_ST   = 0x11
OP_MM   = 0x20;  OP_QACT = 0x21;  OP_QST  = 0x22;  OP_VOP = 0x30

The machine is where the spec's arithmetic becomes behaviour. The MM opcode is the one that matters for LLM work — an exact integer accumulate loop with an fp32 epilogue:

mini/model/sim.py_mmint8 weights, exact integer accumulation, three-multiply epilogue
def _mm(self, w, ra, rb, rc, flags):
    """The exact-integer accumulate loop with the fp32 epilogue (docs/isa.md "MM")."""
    sa  = self.rget(ra) + w[1]      # weight base (DRAM bytes)
    ssa = self.rget(rb) + w[2]      # scale base   (DRAM BYTES, not TMEM words)
    out = self.rget(rc) + w[3]      # TMEM word address
    n  = w[4] & 0xFFFF          # output rows
    kb = (w[4] >> 16) & 0xFF    # K-blocks of depth D
    ab = (w[6] >> 24) & 0xFF
    D  = self.cfg.D

    for j in range(m):
        sw = F.bits(1.0) if unit else None
        for col in range(n):
            accm = 0
            if not unit:
                # the scale row is DRAM: the row's fp32 scale, then one byte per block
                sw = self.rd32(ssa + col * srs)
            for k in range(kb):
                dw = 0 if (unit or (flags & isa.MM_RSC)) else \
                    self.rd8(self._scale_byte_addr(ssa, srs, col, k0 + k))
                for b in range(4):
                    c = 0
                    for i in range(D // 4):
                        actv = self.slice.act[row * self.cfg.ACT_BLOCKS * D
                                              + (ab + k) * D + b * (D // 4) + i]
                        if actv >= 128:
                            actv -= 256                  # ACT RAM is int8
                        wv = self.rd8(sa + col * rs + k * D + b * (D // 4) + i)
                        if wv >= 128:
                            wv -= 256
                        c += actv * wv
                    # the sub-block offset shifts this quarter-block, not the whole accumulator
                    sh = 16 - dw - (0 if unit else self.slice.da[row][ab + k][b])
                    if sh >= 0:
                        accm += (c << sh)
            # epilogue: y = (i2f(acc) * Sw) * (Sa * 2^-W), with W = 16 for int8
            y = F.mul(F.mul(F.i2f(accm), sw),
                      F.mul(self.slice.sa[j * self.cfg.ACT_BLOCKS + ab],
                            F.bits(2.0 ** -16)))
            old = self.tget(out + j * ors + col)
            y = F.add(old, y) if acc else y

Two things in that snippet are already load-bearing for later rungs, and both were documented before the kernels depended on them: ssa is a DRAM byte address (not a TMEM word index), and the epilogue multiplies by 2−W where W = 16 for int8.

What the 28 tests cover

The encoder tests are cheap and exact; the machine tests are the ones that found things:

  • w0's bit layout, and MM's byte lanes (w4 = N | KB<<16 | k0<<24, w6 = ors | M<<16 | ab<<24);
  • R0 reads as 0 and R8..R15 take the run's arguments;
  • LOOP runs, skips on a zero count, nests, and refuses more than four levels;
  • LD/ST move words and reject unaligned DRAM addresses;
  • the quantizer's per-row scale and per-sub-block offsets;
  • an end-to-end program: load two DRAM words, add them as fp32, store — 3.75.

And that forced a hardware change in the same commit: the mini-core's DRAM was sized for a toy. DRAM went 256 KB → 32 MiB and TMEM 4,096 → 8,192 words, because a decode layer's whole activation tile needs 6,416 words and 4,096 could not hold it.

A number we had to fix later

The docstring in this rung said weights total 19,955,712 B (19.0 MiB). It was written before the tensors were read and sized q and o as h×h. The code was corrected when m9 read the checkpoint; the prose wasn't, and stayed wrong for five rungs. Corrected — 24,692,736 B (23.5 MiB) — in a later commit. The lesson is small and general: the number in the comment is the one nothing tests, so it rots first.

One more fact changed the conclusion rather than just a number. With the LM head tied to the embedding, 11.7 MiB serves both roles and the map fits. Untied, the same model needs 35.3 MiB and does not fit 32 MiB at all. Tying isn't an optimisation here; it's the reason the map exists.

rung m5 · +351 lines · 7 files · 9 tests

The decode kernels, and five bugs running them found

PASS matmul · RMSNorm · SwiGLU

The kernels are program fragments emitted through our own encoder — not C, not a compiler. A matmul is four instructions, which is the shortest useful thing to show because each immediate is a different kind of address:

mini/kernels/llama.pymatmul()weight base, scale base and TMEM output, in four instructions
def matmul(weights, out_tmem, n, kb, *, ab=0, rs=None, srs=None, acc=False, rmax=False):
    """One MM: ACT RAM activations against `n` rows of int8 weights streamed from DRAM."""
    rs  = L.HIDDEN if rs  is None else rs    # row stride in the weights (BYTES)
    srs = L.scale_row_bytes(kb) if srs is None else srs
    return [
        isa.li(1, weights),              # R1 = weights
        isa.li(2, weights + rs * n),      # R2 = scale rows FOLLOW the weight bytes
        isa.li(3, out_tmem * 4),          # R3 = MM's out field is a TMEM WORD address
        isa.mm(1, 2, 3, n=n, kb=kb, m=1, ab=ab, rs=rs, ors=1, srs=srs, acc=acc, rmax=rmax),
    ]

RMSNorm is the fragment that shows the ISA's shape most clearly, because the ISA has no divide — the reciprocal square root is a VOP function, and the scalar chain has to live somewhere that isn't the source tile:

mini/kernels/llama.pyrmsnorm()a scalar chain in T_SCRATCH, never touching src
def rmsnorm(src, dst, weight, rows=1, n=None, scratch=None):
    """RMSNorm: y = x * rsqrt(mean(x^2) + eps) * gamma.

    The ISA has no divide, so the reciprocal square root of the mean square is the RSQRT VOP.
    The scalar chain lives in T_SCRATCH and never touches `src`, which the final multiplicands
    still need.
    """
    return [
        # T_SCRATCH = sum(x^2)
        isa.vop(0, 0, 0, 0, dst_imm=sc, a_imm=src, rows=rows, cols=n, func=isa.F_RSSQ),
        # mean = sum * (1/n)
        isa.li(4, _f32_word(1.0 / n)),
        isa.vop(0, 0, 0, 4, dst_imm=sc, a_imm=sc, rows=1, cols=1,
                func=isa.F_MUL, bmode=3),          # bmode=3: b comes from an immediate REGISTER
        # + eps
        isa.li(5, _f32_word(7.5e-6)),
        isa.vop(0, 0, 0, 5, dst_imm=sc, a_imm=sc, rows=1, cols=1, func=isa.F_ADD, bmode=3),
        # the factor
        isa.vop(0, 0, 0, 0, dst_imm=sc, a_imm=sc, rows=1, cols=1, func=isa.F_RSQRT),
        # dst = src * factor           (factor via b_imm, so `src` is untouched)
        isa.vop(0, 0, 0, 0, dst_imm=dst, a_imm=src, b_imm=sc, rows=rows, cols=n,
                func=isa.F_MUL, bmode=2),
        # dst = dst * gamma
        isa.vop(0, 0, 0, 0, dst_imm=dst, a_imm=dst, b_imm=weight, rows=rows, cols=n,
                func=isa.F_MUL, bmode=2),
    ]

The five bugs the tests found

the bugwhat it did
VOP's ra addresses the destination while rd supplies the immediate we passed ra=4, so every TMEM address became R4's fp32 bits. The machine tried to write to address 1069071675 and stopped.
silu negated after exp2 instead of inside the constant computed −exp(x): returned −0.58 for x = 1, where the answer is +0.73.
ACT RAM holds int8, and we read it as unsigned −2 became 254, and a dot product of 33 came out as 1569 — 47× too large.
MM's scale rows are DRAM bytes, not TMEM words the spec's ssa is a byte address; we read it as a TMEM word index.
RMSNorm wrote its reduction into its own source tile then multiplied the clobbered values and returned zeros.
Test the number, not the smoke

Every one of those five produced plausible-looking instructions. A test that checked "does it run" would have passed all five. Only running them on real values catches a sign extension and a negated silu.

One decoder layer, composed

PASS rmsnorm → qkv → attention → wo → mlp → residual

Each kernel being right alone is not the same as them composing. m6 drives one layer in the order a token runs it and compares against the same computation in plain Python over the same quantized weights.

The rung's most important change is structural rather than algorithmic: the layer gets distinct TMEM regions per role instead of reusing buffers. That decision is the whole of Shape's map, and it is worth showing because three of the five bugs below were aliasing inside it:

Five bugs only composition could find

  1. The weight scale rows overlapped the next matrix's weights. The scale base is addr + nrows*in_width, so the next matrix starts at sbase + nrows*srs. We advanced by the scale-row size instead, and gate's scales silently corrupted up's weights. up matched the reference; gate did not. That asymmetry is what gave it away.
  2. rmsnorm's destination aliased its own scratch, so the norm returned zeros.
  3. The matmul output slot was 8 TMEM words wide while a matmul writes hidden of them, so it overlapped the norm tile.
  4. Six fp32 functions needed the flush rules, and max/min must flush operands before comparing, not after.
  5. recip's threshold was one binade low — exponent field 254 instead of 0x7E800000. One binade; a whole class of inputs.
The pattern worth remembering

Four of the bugs on this branch had the same shape: a TMEM region sized or placed wrong. Each was invisible to unit tests, because each component worked alone. What catches that class of bug is not more tests — it's asserting the regions are disjoint. That assertion is a test now, not an eyeball.

def test_the_prediction_matches_the_fp32_reference(decoded):
    """The end-to-end claim: same top tokens, same order, within int8 quantization error."""
    machine   = d.logits(hidden, first=0, count=N_LOGITS)
    reference = _fp32_reference(decoded['ck'])
    got_top = sorted(range(N_LOGITS), key=lambda i: -machine[i])[:2]
    ref_top = sorted(range(N_LOGITS), key=lambda i: -reference[i])[:2]
    assert got_top == ref_top, f'top tokens differ: machine {got_top}, reference {ref_top}'

What we'd have missed by rounding

If we'd called 3× off "within quantization error", we'd have shipped a decoder whose attention silently deleted a head's first context value. It would have produced fluent-looking garbage forever, and every metric except a bit-exact reference would have called it fine.

Scope, stated before the numbers

Everything in this session is synthesis — yosys to technology-mapped LUT/FF/DSP/BRAM, plus Vivado's synth_design. Neither flow ran place-and-route. So nothing below says whether the design fits on the device; it says whether each rung's RTL survives the frontend and the mapper. The place-and-route question is the one still open, and it is named as open at the end.

The instrument

The question "can openXC7 build this" is only worth asking if a failure says where it broke. mini/openflow/measure.py synthesizes each rung's own RTL as a standalone design and classifies the stop:

Both build the toy — and both produce 0 LUTs, 0 FFs. That is not the tools failing. The toy's top has no output ports carrying the datapath, so both tools correctly discard the design as unreachable. Neither finished the mini-core, and neither was stopped by the tool. openXC7 reached technology mapping; Vivado synthesized all eight modules. Then both took SIGTERM from the thermal guard at 97–99 °C, and neither reported an error. So: neither tool has demonstrated a limit here. The host has.

The Vivado-only one is subtle. `default_nettype none leaked across files because nothing restored the default at end-of-file, so Vivado reported "net type must be explicitly specified" at the next file's first port — slang reads each file in isolation and never noticed. And under that directive an input port must name its net type: input logic is a variable declaration Vivado rejects for a port; input wire logic is correct — while an output driven from always_ff must still be a variable. Fixed across 15 files.

So which is better?

  • For iterating on RTL: openXC7. 56× faster on the one rung both completed (4.2 s vs 254.7 s), no licence, and its stricter frontend is a free linter.
  • For producing a bitstream for this card: Vivado. It has produced the actual shipped images, and it is what the board flow documents.
  • For finding bugs: both, because they fail on different things.

What this session did not answer

Place and route is still the open question

The question the goal actually asks is whether openXC7 can place and route the ladder's rungs, not whether it can map them to cells. synth_xilinx stops at the mapped netlist; nextpnr-himbaechel is the stage that places cells and routes wires, and this session never invoked it.

What would have to change first: the rungs that "synthesize" are not yet placeable. The toy's netlist has 0 output ports and 148 IBUFs — nothing to place. And the 32 MiB DRAM is a logic [7:0] mem [0:33554431] behavioural array, which would need ~910 BRAM36 (~47% of an xc7k480t) to exist on-chip. So the synthesis results above are necessary and not sufficient; they do not yet constitute a fit claim, and the blog does not make one.

Seven lessons, one per rung that taught one

1. A ladder that imports tells you nothing

197,981 lines of byte-identical product code is not progress. If the branch can't explain its own diff, the diff is the wrong shape.

2. A specification is not an implementation

Reading docs/isa.md and writing an encoder is authorship. Copying isa.py is not. It cost about 1,500 extra lines, which is a bargain.

3. Bit-exactness needs a model, not a tolerance

The 1-ULP sticky bit is invisible without an oracle that says which 32 bits are correct. Write the model first, then the hardware has something to be wrong against.

4. Test the number, not the smoke

All five kernel bugs produced plausible instructions. And "3× off but right tokens" is still a bug — our own PARTIAL verdict is what forced the isolation pass that found the one-line fix.

5. Units don't compose; regions do

Three of the m6 bugs and the m9 bug were all a TMEM region sized or placed wrong. Assert disjointness; then a wrong address is a failing test instead of a plausible number.

6. Never report a host kill as a toolchain limit

The thermal guard firing at 97 °C is not openXC7 refusing to synthesize. Distinguishing "the tool said no" from "the machine said stop" is the difference between a finding and a fabrication.

7. ALWAYS TRY THE HACKY WAY — then measure what it gave you

Copying the product tree got us a bit-exact proof we still rely on. But the numbers said "half of this is somebody else's code", so we threw the branch away and did it properly. The hack got us the information; honesty made us act on it.

What's next

  • A real bitstream. Neither flow has been allowed to finish the mini-core, because this host kills CPU burners above 97 °C. A scheduling problem, not a toolchain verdict.
  • The card. The hardware rungs stay blocked on a cable that isn't here. The simulation is faithful now; the board run is a different claim and needs different evidence.
  • More than one token. Decoding one token proves the pipeline; decoding a sentence proves the KV cache, which the layout already reserves 4,608 KiB for but no kernel writes yet.

The honest summary: the simulation objective is met — a readable TPU that runs the real TinyStories-15M checkpoint and predicts the same next tokens, in the same order, as an fp32 reference — and the hardware objective is not, because the cable is absent and the host will not let a synthesis run finish.

Nine rungs, 5,175 lines, and the last commit is the one where a real checkpoint finally produced the right answer.
