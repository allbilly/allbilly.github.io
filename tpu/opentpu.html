We built Tiny-TPU because nobody really understands how TPUs work… and neither do we. We had a strict design philosophy: ALWAYS TRY THE HACKY WAY. Draw everything. Reinvent it instead of reverse-engineering it. Learn in public.

Then a while ago someone looked at our 2×2 systolic array, our 128-word unified buffer and our Q8.8 microcode, and asked the obvious question:

okay but can it run an LLM?

No. Obviously not. Our toy TPU does the forward and backward pass of a 2→2→1 XOR network. It does not have an instruction bus, a compiler, DRAM, a host interface, or any concept of a “model” larger than sixteen words. The adult version of this idea — openTPU — is a compiler-driven int8 accelerator with a 256-bit instruction, a tile memory, a systolic matrix unit with per-block scales, a fp32 vector unit, a Triton-style language, a bit-exact simulator, a PCIe and JTAG host stack, and ten different LLMs whose on-card tokens match the simulator bit for bit.

Between those two things there was… a blank page. Every write-up goes from “here’s a matmul” to “and then Qwen 3.5 generates tokens at 8 tok/s.” That is the rest-of-the-owl meme of hardware.

So we built the middle. As a ladder of seventeen commits, each a small machine you can check out, run, and test. This is the story of what we learned on the rungs — and a map if you want to climb it yourself.

The gap is where the understanding lives

A toy TPU teaches you an idea: MACs flow through an array, partial sums drip down, a buffer holds the tiles. A production accelerator teaches you nothing the first time you open it, because it is 55,000 lines of SystemVerilog and 50,000 lines of Python and all of it assumes you already know what a scoreboard is.

The middle is the part with the actual lessons:

  • how a fixed-point 2×2 array becomes a quantized 8-column MXU,
  • how microcode becomes an instruction set with loops and registers,
  • how “load a tile” becomes DMA, DRAM, a quantizer, and a scale-row layout,
  • how a Python program becomes an image on a card, and
  • how you know any of it is right, when the hardware sits on another desk.

Here’s the trick that made the whole thing tractable: we didn’t start from Tiny-TPU. We started from the end, and built the ladder downwards.

The end was already here — openTPU, a tree that runs real LLMs on a real Xilinx Kintex-7 card. That tree also ships a bit-exact ISA simulator. Every instruction you can run on the hardware, you can run in Python, word for word, cycle semantics included. Which gives us the one thing a toy project never has:

an oracle.

Rule #1: the simulator is the grown-up in the room

Here’s the thing about hardware: it lies. Not on purpose — it just has more states than you have test benches. A stray latch, an off-by-one in a loop counter, a multiplier that flushes denormals when the spec says round-to-nearest-even: all of it produces something, and the something looks plausible right up until the tokens are wrong.

The production openTPU test methodology is brutal and beautiful: run the same program on the RTL and on the ISA simulator, then compare every TMEM word and every DRAM byte. No tolerance. No np.allclose. No “close enough for ML.”

We borrowed that. Every rung in the ladder from step 3 onwards is graded by the same rule: RTL versus isasim, whole-state equality, bit for bit. Fingerprints of wrongness show up immediately — a wrong scale row changes one word, a wrong sum order changes a value in the last ulp, a wrong quantizer offset changes a whole block at once.

And yes, chasing the last ulp taught us more about the design than any diagram ever did.

The ladder

Seventeen rungs. Each one is a commit you can check out and run; each ships its own tests and its own machine-readable receipt.

Steps 12, 13 and 15 are the ones that touch the physical card — and our card’s JTAG cable wasn’t attached while we did this. Those rungs are committed with honest BLOCKED receipts and a read-only probe that says exactly why, plus the exact commands to finish them when the cable comes back. No fake PASS. Ever. The other fourteen rungs are green: 360 test cases, from 14 to 102 per rung.

Seventeen rungs, one by one

The rest of this post climbs the ladder one rung at a time, and every rung is its own section: a real commit, its own machine, its own tests and its own diagram. Read it in order, or use the index above to jump to the one you are curious about.

rung 02 · toy

Step 2 · the scoreboard, and the bug it found

PASS9 tests

Then our own testbench got caught lying. The imported XOR test had no scoreboard; it pulsed sys_switch_in one cycle too early, so both rows of the systolic array latched the same weight, and the network quietly computed (x0 + x1) · w instead of a dot product. It had been “passing” forever, because a test with no scoreboard can’t fail — it just draws a waveform that nobody reads.

We fixed the timing, then built a scoreboard: golden vectors from a tiny independent Q8.8 model at every stage boundary, plus a mutation test that breaks one module at a time and demands that the bench fail. Five modules that had been smoke-tested forever became genuinely tested — 5/5 mutations caught.

# ladder/bench/toy_golden.py — the independent Q8.8 model the bench checks
def fmul(a, b):
    prod = a * b                 # Q16.16
    r = prod >> 8                # floor to Q8.8
    if (prod >> 7) & 1 and (r & 0x7FFFFF) != 0x7FFFFF:
        r += 1                   # round-half-up, exactly like fxp_zoom
    return clip16(r)

def fadd(a, b):  return clip16(a + b)
def leaky(x, leak):  return x if x >= 0 else fmul(x, leak)

rung 03 · contract

Step 3 · sign the contract before writing RTL

PASS61 tests

Before writing a single line of new hardware description, we imported the openTPU ISA document, instruction encoder, bit-exact simulator, fp32 arithmetic model and quantizer — byte-identically. That is the contract: encodings, arithmetic semantics and the memory model. From this rung on, every hardware decision had a Python referee. If the RTL and the simulator disagree by one word, the RTL is wrong.

It feels backwards to start a hardware project by importing software. It’s the best decision we made.

# opentpu/isa.py — the contract, and the only encoder anyone may use
def encode(self) -> list[int]:
    w0 = (self.op & 0xFF) | (self.ra << 8) | (self.rb << 12) \
        | (self.rc << 16) | (self.rd << 20) | ((self.flags & 0xFF) << 24)
    return [u32(w0)] + [u32(x) for x in self.w]      # 8 × 32 = 256 bits

# and the oracle: opentpu/isasim.py — every instruction, cycle semantics
# included, pure Python.  From here on, "correct" means "isasim agrees".

rung 06 · mini-core

Step 6 · quantization, exactly

PASS27 tests

Quantization is where an accelerator stops being arithmetic and starts being a data format. Per row: compute amax, derive S = amax/127, apply the per-group power-of-two scale, round half-to-even, saturate to int8. The scale row (Sa/da) travels beside the data in the activation RAM. The corner that cost us the most was 0 × inf = NaN → 0.

27 tests, and every output word had to equal the simulator’s — scales included.

rung 07 · mini-core

Step 7 · the matrix unit

PASS31 tests

The matrix unit is the scary one. Exact integer accumulation over D-byte blocks, then a window of shifts sh = 16 − dw − da — which is signed, can be −494, and then whole groups get dropped — then an fp32 epilogue with three multiplies in a very specific association. The generic int→fp32 converter truncated, so we built a 48-bit one.

Thirty-one tests, bit for bit.

rung 08 · mini-core

Step 8 · reductions, argmax, outer

PASS33 tests

Reductions look trivial until you need the same bits as the hardware: row sums are sixty-four interleaved partials, with +0 padding actually added, folded by a tree of exactly 63 adds. A flat sum is not bit-identical, and softmax does not forgive. Add argmax and the outer product and the attention ingredient list is complete.

rung 14 · llm

Step 14 · an LLM that fits on a napkin

PASS3 tests

And then the fun one. openTPU’s simulator can run real transformers; so can the RTL. But checkpoints are gigabytes and this host has no torch — so we build a tiny Qwen3 with numpy: 256 hidden, two layers, four query / two KV heads, head_dim 128, vocab 1000, default_rng(0). No tokenizer, no checkpoint, no GPU. It produces a 2.2 MB image, and the prompt [811, 85, 179, 236, 181] greedily continues as [181, 181, 181, 564, 564, 564] — the same six tokens on the simulator and on the production RTL, with logits and the whole DRAM image equal bit for bit.

That’s the moment the ladder reaches “LLM inference,” on a machine nobody would call a computer.

What we’d tell ourselves at the start

  1. Start from the end. The reference implementation you’re scared of is not your enemy; it’s the answer key. Read it, import its contracts, and build the small version yourself.
  2. Make the simulator the boss. If you can’t state “these two machines must be identical bit for bit,” you don’t have a test — you have a vibe.
  3. Write receipts. Every rung writes a JSON receipt: commit, command, toolchain, per-test verdicts, thermal state. “It worked on my machine” becomes “here’s the file.”
  4. Build the toy version first, then delete it. The mini-core is dead code — that’s the point. Its tests outlive it.
  5. Let the hardware be a jerk. Compilers take minutes, timing takes hours, thermal throttling takes your afternoon. Design the test tiers so the fun part is cheap.
  6. Keep the failed attempts. The upstream bug we found, the wrong epilogue association, the 600-second timeout that hid a frozen process — they’re the most educational lines in the history.
  7. One rung per commit. A clean path is a gift to whoever climbs after you, including future you.
